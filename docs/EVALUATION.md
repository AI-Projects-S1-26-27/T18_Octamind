# Evaluation, ablation and error analysis (Role 8)

Code: `src/evaluation/` (`metrics.py`, `run.py`, `splits.py`, `ablation.py`, `error_injection.py`, `plots.py`).

## Metrics

- **Exact Match (EM):** SQuAD-style normalization; takes the maximum match against the gold answer and dataset answer aliases.
- **Token F1:** normalized token overlap, maximized over aliases.
- **Evidence recall/precision/F1:** retrieved paragraph IDs compared with Role 1 gold supporting paragraph IDs. This is independent of answer generation.
- **Path recall:** for records with a gold reasoning chain, selected edge triples are compared with the edges generated by the repository's oracle-chain conversion; omitted when no usable gold chain exists.
- **Context tokens:** shared deterministic `regex_wordpunct_v1` count over the evidence context. It is comparable across systems but is not Gemini's native tokenizer. Full-prompt regex count and provider-reported prompt/output usage are stored separately where available.
- **Search effort:** nodes expanded, peak frontier size, beam/relevance pruning and traversal latency from Roles 5/6.
- **Failure categories:** retrieval failure when evidence recall is below 1; generation failure when evidence recall is 1 but the answer is incorrect; answer-not-generated if no answer is present. Fine-grained stage labels are diagnostic heuristics, not verified causal attributions.
- **Paired bootstrap:** resamples matched question-level differences and reports a two-sided 95% percentile confidence interval. Comparisons require identical question IDs.

The proposal defines context reduction at matched accuracy as `CR = 1 - T(proposed) / T(vector RAG)`, where `T(m)` is the mean context size of a method at the target F1. The evaluation runner selects the S2 vector-RAG configuration and S6 operating point on tuning IDs only. On held-out test IDs it evaluates those locked configurations; it reports context reduction only if the locked S6 setting reaches the locked S2 setting's test F1. It does not retune on the test set.

## Deterministic tuning/test split

Create one hop-stratified split and reuse it for every system:

```bash
python -m src.evaluation.splits --dataset musique --tune-fraction 0.2 --seed 0
```

The split manifest is written to `results/evaluation/musique_split.json`. For the 600-question MuSiQue sample, a 20% tuning fraction yields 40 tune questions per hop (120 total) and 160 test questions per hop (480 total). Actual counts are printed in the manifest. Do not regenerate or change this split between systems.

Each runner accepts `--split-manifest` and `--split-part tune|test`. Use the same IDs for S1-S3, S6 and S7. The complete sampled corpus is still used for shared-corpus vector indexing and provenance resolution; only the evaluated question list is filtered to the selected split.

## Ablation configurations

Generate proposal-defined configurations:

```bash
python -m src.evaluation.ablation
```

The generator writes signal-removal configs (`alpha`, `beta`, `eta`, `gamma`), search strategies (uniform-cost, greedy best-first, A*-style and weighted A*), beam widths/margins, path-relevance pruning, selection/budget sweeps, and a Role 6 no-source-sentences config under `configs/context_ablations/`. These are configurations only; each run must be executed and its output retained before results are reported.

Use copies of the config and stable tags for all runs. Select weights and budgets from tune IDs only. Do not treat the temporary `epsilon=-5` plumbing check as an ablation result; it was only used to verify the Role 5 selector's output path with random mock vectors.

## Error injection for RQ4

`src.evaluation.error_injection` creates isolated graph copies and never overwrites the source graph:

- **Random edge deletion:** removes a fraction of unique facts and rebuilds inverse edges; no new embeddings are required.
- **Corrupted tail entity:** replaces tails and re-embeds every changed triple using the configured shared embedding service.
- **Wrong entity merges:** merges entity IDs and re-embeds every changed triple.

Run rates 0.10, 0.20 and 0.30 with fixed seeds. Tail and merge changes use batched `embed_many` calls so changed edge text does not retain stale vectors. Mock-mode corruption is for plumbing only; research runs require the same real embedding model as the uncorrupted graph.

Example (after real Gemini embeddings are available):

```bash
python -m src.evaluation.error_injection --dataset musique \
  --corruptions deletions tail merge --rates 0.1 0.2 0.3 --seed 0 \
  --embedding-mode gemini
```

Each graph is written beneath `data/graph_perturbed/<corruption>_<rate>/musique/`. Pass the corresponding directory to Role 5/6/7 with `--graph-dir`, for example `--graph-dir data/graph_perturbed/deletions_0.10`. Use the same tune/test manifest and evaluate the same question IDs at every corruption level.

## Run the final evaluation

First generate answer-bearing JSONL rows for every system using the same Role 6 prompt and the same answer model. The recommended multi-step order is documented in `docs/FINAL_RUNBOOK.md`. The evaluator expects one row per question per variant, with fields including `question_id`, `system`, `context_tokens`, `retrieved_paragraph_ids`, `gold_paragraph_ids`, and `answer`.

Then combine tuning and held-out files (the evaluator separates them using the manifest):

```bash
python -m src.evaluation.run --dataset musique \
  --inputs <all-tune-and-test-answer-jsonl-files> \
  --split-manifest results/evaluation/musique_split.json \
  --tag heldout
```

The evaluator verifies that every variant covers exactly the expected tune/test question IDs and rejects overlap/unknown IDs. It writes `*_scored.jsonl`, `*_summary.json`, and `*_summary.csv` under `results/evaluation/`.

Optional plots:

```bash
python -m src.evaluation.plots --summary results/evaluation/musique_heldout_summary.json
```

Install `matplotlib` in the project environment if the optional chart command reports it is missing.

## Known scope limits

This module supplies evaluation and experiment tooling, not experimental findings. Current local tests are synthetic/API-free tests. Real Gemini embeddings and answers, weight tuning, S1-S3/S6/S7 held-out runs, and RQ4 runs still have to be executed with the team's credentials and datasets. S4 HippoRAG (LightRAG fallback) is not integrated in this repository; optional S5 IRCoT is also not implemented. Do not label S1-S3 as S4/S5, and do not report mock-embedding runs as research evidence. If S4 cannot be integrated reproducibly before submission, state that explicitly in Results/Limitations.
